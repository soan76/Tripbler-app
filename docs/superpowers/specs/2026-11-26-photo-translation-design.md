# 사진 번역(촬영 → AI 보정·번역 → 사진 위 흰 상자) 설계

- 작성일: 2026-11-26
- 상태: 사용자 승인(2026-11-26, 백업·비저장·설정값·연동 순서 보완 포함). 구현은 시작하지 않았다.
- 범위: 앱(`lib/`)과 백엔드(`backend/`)

## 1. 의도와 이유

번역 탭에서 실시간 번역을 없애고 "찍어서 읽는" 흐름 하나로 간다. 사용자가 원하는 일은 **찍은 글의 뜻을 편하게 읽는 것**이다. 그래서 번역을 사진 속 원문 자리에 흰 상자로 덮어 보여 주고, 다른 정보는 상자를 눌렀을 때만 보여 준다.

AI(사진을 보는 모델)는 기기 OCR이 틀린 글자를 사진과 대조해 바로잡는다. 하지만 AI 보정은 정확성을 보장하지 않는다. 그래서 불명확한 글자는 추측하지 않게 하고, 읽지 못한 부분과 대체 번역은 사용자에게 드러낸다.

## 2. 목표 · 비목표 · 실패 조건

**목표**
- 전체 화면 카메라로 찍으면 사진이 고정된다. 그 사진 위 원문 자리에 문단별 번역이 흰 상자로 나타난다.
- 사진과 상자를 함께 확대하고 이동할 수 있다. 원문 보기와 재촬영도 할 수 있다.
- 상자를 누르면 그 문단의 원문, 번역, 한글 발음, 원화 가격이 상세로 나온다.
- 읽지 못한 부분과 OCR 글자만으로 번역한 문단을 문단마다 표시한다.
- 사진 전송 전에 동의를 받는다. 동의는 안내 버전과 함께 저장한다.

**비목표(이번 설계에서 하지 않음)**
- 실시간 번역과 응답을 나눠 받는 표시(문단별 순차 표시)
- 서버 OCR
- 사진 보관 기능, 번역 기록
- 기존 `/api/v1/translation/lines`와 줄 목록 결과 화면 삭제(새 흐름이 자리 잡은 뒤 따로 정리)
- 모델 확정(아래 9절 측정 뒤 결정)

**실패 조건(동작해도 실패로 본다)**
- AI가 보이지 않는 글자를 그럴듯하게 지어내 확정된 번역처럼 보여 준다.
- 불확실한 가격을 확정된 원화 금액으로 보여 준다.
- 대체 번역인데 그 사실을 알리지 않는다.
- 동의 전에 사진이나 글자를 보낸다.
- 취소·재촬영 뒤 도착한 이전 응답이 새 화면에 반영된다.
- 확대·이동할 때 상자가 사진 속 원문 자리에서 어긋난다.
- 확인하지 않은 보관·삭제·학습 정책을 앱 문구로 약속한다.

## 3. 제약

- 기존 구조를 따른다: 화면 → Notifier → Service, Riverpod 3, 파일 450줄 규칙(`AGENTS.md`). 백엔드는 `controller → service → client`, DTO 검증, `ErrorCode` 규칙을 따른다(`backend/AGENTS.md`).
- 백엔드 multipart 한도는 파일 5MB, 요청 6MB다(`application.properties`). 이 한도 안에서 설계한다.
- 번역 API는 로그인이 필요하고 호출 제한이 있다(`backend/docs/translation-lines-api.md`). 새 API도 같은 원칙을 따른다.
- 사진과 인식 글자는 개인정보일 수 있다. 앱과 서버 모두 로그에 남기지 않는다. 크기, 개수, 시간 같은 숫자만 남긴다.
- Claude 실제 호출은 아직 확인하지 못했다(크레딧 0). 모델, 지연, 비용이 정해지지 않았다는 전제로 설계한다.

## 4. 검토한 방법과 선택

| 방법 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 한 번에 보내고 받기(선택)** | 정리한 사진과 문단 목록을 새 API 한 번으로 보내고, 문단별 결과를 한 번에 받는다 | 구조가 단순하다. 상자가 한 번만 나타난다 | 결과가 나올 때까지 기다려야 한다 |
| B. 빠른 번역 먼저, AI 보정 나중 | 글자만으로 먼저 번역해 보여 주고, AI 결과로 바꿔 끼운다 | 첫 화면이 빠르다 | 읽는 중에 상자가 바뀐다. 비용이 두 배다 |
| C. 문단별 순차 표시 | 응답을 나눠 받아 문단마다 상자를 띄운다 | 체감 속도가 가장 좋다 | 서버와 앱이 모두 복잡하다 |
| (제외) 서버 OCR | 사진만 보낸다 | — | 기기 OCR로 문단 ID·좌표를 만든다는 결정과 맞지 않는다 |

사용자가 **A**를 골랐다. 9절 측정에서 지연이 문제로 드러나면 그때 C를 다시 검토한다.

## 5. 전체 흐름

```
[촬영 화면: 전체 화면 카메라, 하단 안내 "촬영한 사진은 AI 번역을 위해 전송됩니다"]
   │ 셔터(또는 갤러리)
   ▼
① 사진 정리(기기): EXIF 회전 적용 → 긴 변 축소(시험값 2048px) → JPEG 임시 파일
   ▼
② OCR(기기, 정리한 사진으로): 줄 + 줄 상자 + 덩어리 번호 → 문단 묶기 → 문단 ID 부여
   ▼
③ 동의 확인: 저장된 동의 버전이 현재 버전보다 낮거나 없으면 동의 안내
   │   취소 → 아무것도 보내지 않고 촬영 화면으로
   ▼ 동의함(또는 이미 동의)
④ 전송: POST /api/v1/translation/photo (사진 + 문단 목록)
   ▼
⑤ 결과: 사진 위 흰 상자(번역만). 확대·이동, 원문 보기, 재촬영, 상자 누르면 상세
```

- ①과 ②는 동의 전에 기기 안에서만 처리한다. ③의 안내는 처음 찍은 뒤, 업로드 직전에 나온다(사용자 결정).
- ②에서 글자가 하나도 없으면 ③④로 가지 않는다. "글자를 찾지 못했어요"와 재촬영을 보여 준다(제 판단).
- 갤러리에서 고른 사진도 ①부터 같은 흐름을 탄다. 동의 안내도 똑같이 나온다(제 판단: 갤러리 고르기는 기존 기능이라 유지한다).

## 6. 앱 설계

### 6.0 번역 탭 연결
- 8.2의 5단계(실제 연동 확인과 실기기 확인)를 마치면 번역 탭의 찍기 흐름을 **한 번에 바꾼다**. 두 흐름을 함께 두지 않고 전환 스위치도 두지 않는다(제 판단: 사용자가 "이 흐름 하나로 전환"을 정했다).
- 그 시점부터 앱은 `/lines`, 줄 목록 결과 화면, `CaptureFrame` 프레임 선택을 부르지 않는다. 코드 삭제는 11절대로 나중에 따로 정한다.
- 기존 `translation_provider`를 고칠지 새 Notifier를 만들지는 구현자가 정한다. 다만 바꾸는 시점에 번역 탭이 부르는 흐름은 하나여야 한다.

### 6.1 촬영 화면
- 카메라 미리보기가 번역 탭 화면 전체를 채운다(cover). 지금의 3:4 카드와 가이드 프레임(`CaptureFrame`)은 새 흐름에서 쓰지 않는다. 사진 전체를 OCR한다.
- 하단에 고정 안내 "촬영한 사진은 AI 번역을 위해 전송됩니다"를 둔다(사용자 결정). 보관·삭제·학습 여부 문구는 넣지 않는다. 정책을 확인한 뒤 별도로 정한다.
- 셔터, 갤러리, 플래시, 언어 선택을 둔다. 원문 언어 선택은 지금처럼 `auto`를 기본으로 유지한다(제 판단). OCR 문자 체계를 고르는 데 필요하기 때문이다.
- 미리보기는 cover라서 화면에 보이던 범위보다 실제 사진이 조금 더 넓을 수 있다. 결과 화면은 사진 전체를 보여 준다(contain).

### 6.2 사진 정리와 좌표계
- 촬영 직후 사진 하나를 기준 사진으로 만든다.
  - EXIF 방향을 픽셀에 반영한다.
  - 긴 변을 **시험값 2048px** 이하로 줄인다. 작은 글씨 인식 품질을 확인한 뒤 확정한다(사용자 결정).
  - JPEG(품질 시험값 85)로 앱 임시 폴더에 저장한다.
- **OCR 입력, 서버 전송, 화면 표시 모두 이 기준 사진 하나를 쓴다.** 그러면 OCR 좌표, AI가 보는 사진, 화면의 사진이 같은 픽셀 좌표계가 된다. 회전과 크기 조정은 ①에서 한 번만 일어난다.
- 기준 사진의 가로·세로 픽셀을 함께 들고 다닌다. 서버에도 보내서 서버가 실제 사진 크기와 대조한다(7.2).
- 임시 파일은 결과 화면을 떠날 때, 재촬영할 때, 취소할 때, 화면을 제거할 때 지운다.
- 이미지 디코딩, EXIF, JPEG 인코딩에 쓸 도구는 구현할 때 정한다(12절). 새 의존성이 필요하면 이유를 보고한다.

### 6.3 OCR과 문단
- `OcrService`에 줄 상자와 덩어리 번호를 함께 돌려주는 메서드를 더한다. 지금 `recognizeLines`는 글자만 돌려준다.
  - 기존 `recognizeLines`와 `recognizeText`는 기존 흐름이 남아 있는 동안 그대로 둔다.
  - `auto`일 때는 지금처럼 문자 체계 4가지로 읽고, 글자가 가장 많은 결과를 쓴다.
- 문단 묶기는 `lib/domain/translation/text_paragraphs.dart`의 `buildTextParagraphs`를 쓴다.
- 상자는 축에 맞춘 사각형(ML Kit `boundingBox`)이다. 기울어진 간판이나 세로쓰기 글은 상자가 원문보다 넓게 덮일 수 있다. 이번 범위에서는 이것을 알려진 한계로 둔다(제 판단).
- 문단 ID는 읽는 순서(위→아래, 왼→오른쪽)대로 `p1`, `p2`, … 로 붙인다. 한 요청 안에서만 유일하면 된다.
- 문단 수와 글자 수 상한은 7.1의 서버 한도와 같게 둔다. 넘으면 앞에서부터 한도까지만 보내고, "일부만 번역했어요"를 알린다(제 판단).

### 6.4 동의
- 안내 문구(사용자 결정): "번역을 위해 촬영한 사진과 인식된 글자를 Tripbler 서버 및 AI 제공업체에 전송합니다."
- 버튼은 **동의하고 번역**과 **취소** 두 개다.
  - 취소하면 아무것도 보내지 않고, 임시 사진을 지운 뒤 촬영 화면으로 돌아간다.
  - 뒤로가기나 바깥 누르기도 취소로 본다(제 판단).
- 동의 기록은 `{version, acceptedAt}`를 기기(`shared_preferences`, 기존 `LocalStorageService` 방식)에 저장한다(제 판단).
- 앱에는 현재 안내 버전 상수가 있다. 저장된 버전이 없거나 현재 버전보다 낮으면 다시 안내한다.
  - 전송 대상이나 목적이 바뀌면 버전을 올린다(사용자 결정).
  - 예: AI 제공업체 추가, 보관 정책 변경
- 동의는 **기기에만 저장**하고 서버에는 기록하지 않는다(사용자 결정). 그래서 계정이 아니라 기기 기준이다.
  - 로그아웃하거나 다른 계정으로 바꿔도 다시 묻지 않는다.
  - 앱을 지우거나 기기를 바꾸면 다시 묻는다.
- **OS 백업·복원**(사용자 요구)
  - 이 앱의 `AndroidManifest`에는 `allowBackup` 설정이 없다. 그래서 Android 기본값대로 `shared_preferences`가 자동 백업되고, 새 기기에 복원될 수 있다. iOS의 `UserDefaults`도 iCloud·기기 백업에 들어간다.
  - 규칙: **복원된 동의는 이 설치에서 한 동의로 확인될 때만 유효하다. 확인할 수 없으면 다시 묻는다**(안전한 쪽).
  - 동의 기록에는 설치 표식을 함께 저장한다. 표식은 복원되지 않는 저장소에 둔다(예: iOS 키체인 `*_this_device`, Android에서 복원되면 복호화되지 않는 보안 저장소). 저장된 표식과 지금 설치의 표식이 다르거나 읽을 수 없으면, 동의가 없는 것으로 본다.
  - 구체적인 방식은 구현할 때 정하고, 실기기 백업·복원으로 확인한다.
  - 안내 버전 규칙은 그대로 유지한다. 표식이 맞아도 저장된 버전이 현재 버전보다 낮으면 다시 묻는다.

### 6.5 결과 화면
```
┌─────────────────────────────┐
│ ← 재촬영              원문 보기 │  ← 원문 보기: 상자를 모두 숨김(다시 누르면 보임)
│ ┌───────────────┐            │
│ │ 라멘 정식       │            │  ← 흰 상자: 번역만
│ └───────────────┘            │
│        (사진, 두 손가락 확대·이동) │
│ ┌─────────────────────────┐  │
│ │ 매주 [읽을 수 없음] 휴무  ⚠ │  │  ← 불확실 문단 표시
│ └─────────────────────────┘  │
│ ┌──────────────┐             │
│ │ 영업시간 11시~ ⓘ│             │  ← 이 문단은 대체 번역
│ └──────────────┘             │
│ ⓘ 일부 문단은 글자만으로 번역했어요 │  ← 대체 문단이 하나라도 있으면
└─────────────────────────────┘
상자 누름 → 아래 시트: 원문(보정된 원문) · 번역 · 한글 발음 · 가격(원화) · 표시 이유
```
- **함께 움직이기**: `InteractiveViewer` 안에 "화면에 맞춘 크기(contain)"의 `Stack[사진, 상자]`를 넣는다. 상자 좌표는 `기준 사진 좌표 × 맞춘 배율`로 한 번만 바꾼다. 확대·이동은 둘을 함께 변환하므로 어긋나지 않는다. 실시간 때 쓰던 `live_overlay_mapping`은 쓰지 않는다.
- **상자 그리기**: `lib/widgets/translation/translation_box_overlay.dart`의 `TranslationBoxOverlay`를 쓴다. 상자를 눌러야 하므로 두 가지를 바꾼다.
  - 지금의 `IgnorePointer`를 걷어 낸다.
  - 배치된 상자 영역으로 터치를 판정하는 기능을 더한다.
- 글자 최소 크기는 확대하기 전(맞춘 크기) 기준이다. 확대하면 글자도 함께 커진다.
- **결과 기다리기**: 사진을 먼저 보여 주고, 그 위에 진행 표시와 "번역하는 중"을 띄운다. 이때도 재촬영(=요청 취소)을 누를 수 있다.
- **상세 시트**: 보정된 원문, 번역, 한글 발음, 가격을 보여 준다. 불확실이나 대체 번역이면 그 이유를 한 줄로 적는다. 가격 표시는 7.4를 따른다.
- **실패**: 429, 네트워크 실패, 503이면 사진을 그대로 둔다. "번역하지 못했어요"와 다시 시도, 재촬영을 보여 준다. 다시 시도할 때 같은 기준 사진을 다시 보낸다. 이미 동의했으므로 다시 묻지 않는다.
- **응답에 없는 문단**: 7.3의 ID 검증으로 빠진 문단은 상자를 그리지 않는다. 그 문단은 상세에서 "번역하지 못한 문단"으로 셀 수 있게 남긴다(제 판단).

### 6.6 늦은 응답 무시
- 번역 Notifier는 지금(`translation_provider.dart`의 `_requestId`)처럼 작업 번호를 가진다. 아래 경우에 번호를 올린다.
  - 새 촬영
  - 동의 취소
  - 재촬영
  - 결과 화면 이탈
  - 탭 이탈
  - 다시 시도
  - 화면 제거
- 응답이 오면 작업 번호가 같고 Notifier가 살아 있을 때만 반영한다. 번호가 다르면 버린다.
- 진행 중인 HTTP 요청은 가능하면 끊는다(클라이언트 닫기). 끊지 못해도 번호 검사로 반영을 막는다.
- OCR 결과도 같은 번호 검사를 거친다. 그래서 OCR 중에 재촬영하면 이전 OCR 결과가 동의 안내로 이어지지 않는다.

## 7. 백엔드 설계

### 7.1 API 계약(초안)
`POST /api/v1/translation/photo` — 로그인 필요. `multipart/form-data`로 받는다.

- `image`: 기준 사진. JPEG, 5MB 이하.
- `request`(JSON 파트):
```json
{
  "sourceLanguageCode": "auto",
  "targetLanguageCode": "ko",
  "imageWidth": 1536,
  "imageHeight": 2048,
  "paragraphs": [
    { "id": "p1", "text": "ラーメン定食 ¥980", "box": { "left": 120, "top": 340, "width": 610, "height": 72 } }
  ]
}
```
- 한도(시험값, 기존 줄 번역 한도에 맞춤): 문단 1~50개, 문단당 300자, 전체 4000자. ID는 `^p[0-9]{1,3}$` 형식이고 요청 안에서 중복이 없어야 한다.

응답(200):
```json
{
  "sourceLanguageCode": "ja",
  "targetLanguageCode": "ko",
  "paragraphs": [
    {
      "id": "p1",
      "original": "ラーメン定食 ¥980",
      "translated": "라멘 정식 980엔",
      "uncertain": false,
      "translationSource": "AI",
      "pronunciation": "라멘 테이쇼쿠",
      "prices": [
        {
          "text": "¥980", "amount": 980, "currency": "JPY", "confirmed": true,
          "krwAmount": 9100, "krwRate": 9.29, "rateFetchedAt": "2026-11-26T09:00:00", "rateStale": false
        }
      ]
    }
  ]
}
```
- `prices`는 문단 안의 가격 목록이다. 0개 이상이고 원문 순서를 따른다. 메뉴판처럼 문단 하나에 가격이 여럿일 수 있어 배열로 둔다(제 판단). 상세 시트는 가격을 모두 보여 준다.
- `pronunciation` 규칙은 `/lines`와 같다. 원문이 이미 번역 언어이거나 숫자·기호뿐이면 null이다. 번역 언어 선택은 지금처럼 유지한다(제 판단).
- `original`은 AI가 사진과 대조해 보정한 원문이다. 대체 번역이면 OCR 원문 그대로다.
- `translationSource`는 `AI`(사진 대조 번역) 또는 `OCR_TEXT`(OCR 글자만으로 한 대체 번역)다. **문단마다** 붙는다(사용자 결정).
- `uncertain`이 true면 읽지 못한 부분이 있다는 뜻이다. 읽지 못한 부분은 `original`과 `translated` 안에서 **고정 표시 `[읽을 수 없음]`** 으로 남긴다. 앱은 이 표시를 다른 색으로 그린다. 표시 문자열은 서버와 앱이 같은 상수를 쓴다(제 판단).
- 오류는 기존 `ErrorResponse` 형식을 따른다.
  - 400: 검증 실패(ID 형식·중복, 크기 불일치, 한도 초과, JPEG 아님)
  - 401
  - 413: multipart 한도 초과
  - 429: `Retry-After` 포함
  - 503: AI와 대체 번역이 모두 실패

### 7.2 요청 검증
- 사진의 머리 정보로 실제 가로·세로를 읽는다. `imageWidth`·`imageHeight`와 다르면 400이다. 서로 다른 좌표계를 섞지 않기 위해서다.
- 문단 상자는 사진 안에 있어야 한다(2% 여유). 넓이가 0인 상자는 400이다.
- **Tripbler 쪽 비저장**(사용자 요구, 아래 범위를 모두 검증한다)
  - 사진과 글자는 요청을 처리하는 동안 메모리에만 둔다. 서버는 디스크에 저장하지 않고 로그에도 남기지 않는다.
  - multipart 임시 파일: Spring은 `file-size-threshold`(기본 0)보다 큰 파트를 임시 디렉터리에 쓴다. 사진 API에서는 임계값을 요청 한도 이상으로 올려 디스크에 쓰지 않게 한다. 그래도 쓰인 파일이 없는지 테스트로 확인한다.
  - 프록시: 지금은 프록시 없는 단일 서버다(`translation-lines-api.md`). 앞으로 프록시를 두면 요청 본문 버퍼링(예: nginx `client_body_temp`)과 접근 로그 설정을 같은 기준으로 다시 검증한다.
  - 오류·접근 로그: 예외 처리(`GlobalExceptionHandler`), 검증 실패 메시지, Anthropic SDK·HTTP 클라이언트 로그에 사진 바이트·base64·인식 글자·번역문이 들어가지 않아야 한다. 크기, 개수, 시간, 오류 종류만 남긴다.
  - 앱: 기준 사진 임시 파일을 6.2대로 지운다. 앱 로그에도 글자 내용을 남기지 않는다. 기존 `recognizeText`의 디버그 출력은 새 경로에서 쓰지 않는다.
- **AI 제공업체 보관은 별개다**: 위 항목은 Tripbler가 통제하는 범위다. Anthropic 등 제공업체가 사진과 글자를 얼마나 보관하는지, 학습에 쓰는지는 제공업체 정책과 계약(조직 설정 포함)으로 정해진다. 그래서 따로 확인하고 따로 적는다. 앱 안내 문구에 보관 정책을 넣을지는 둘 다 확인한 뒤 정한다.

### 7.3 AI 호출과 문단 ID 검증
- 새 클라이언트(`PhotoTranslationClient` 인터페이스와 Claude 구현)를 둔다. 사진 1장과 문단 목록 JSON을 보내고, 구조화 출력으로 받는다.
- 프롬프트 원칙(사용자 결정을 지시로 옮김):
  - OCR 글자는 참고용이다. **사진에서 분명히 보일 때만** 고친다.
  - 흐리거나 잘리거나 가려진 글자는 추측하지 않는다. `[읽을 수 없음]`으로 남기고 `uncertain: true`로 표시한다. 읽을 수 있는 부분은 번역한다.
  - 문단 ID를 그대로 쓴다. 문단을 합치거나 쪼개거나 새로 만들지 않는다.
  - 가격은 사진과 대조해 금액과 통화를 적고, 확실하지 않으면 `priceUncertain: true`로 표시한다.
- **ID 검증(서버)**: AI 응답의 ID 집합을 요청 ID 집합과 비교한다.
  - 모르는 ID와 중복 ID는 버린다.
  - 빠진 ID는 그 문단만 **문단별 대체 번역**(OCR 글자로 Google 번역, `translationSource: OCR_TEXT`)으로 채운다.
  - AI 호출 자체가 실패하면(시간 초과, 거절, 해석 실패, 키·크레딧 없음 등 지금 `/lines`와 같은 기준) 모든 문단을 대체 번역으로 채운다.
  - 대체 번역까지 실패하면 503이다.
- **ID 검증(앱)**: 응답 ID를 보낸 문단 ID와 다시 대조한다. 모르는 ID는 무시하고, 빠진 문단은 6.5대로 처리한다.
- AI에는 사진, 문단 ID, OCR 원문과 함께 **문단 상자 좌표도 보낸다**. 어느 글자가 사진의 어느 자리인지 맞추는 데 도움이 되기 때문이다(제 판단). 토큰 증가분은 9절에서 함께 잰다.
- 모델 이름은 설정값(`translation.photo.model`)으로 둔다. 기본값은 9절 측정 뒤 정한다. SDK 재시도는 지금처럼 끈다.
- 구현 중 임시값(제 판단):
  - 서버 시간 제한과 `max_tokens` 계수는 `/lines`와 같게 둔다(30초 + 글자당 12ms, 최대 90초).
  - 앱 HTTP 시간 제한도 `/lines`와 같은 120초로 둔다.
  - 구현과 테스트는 가짜 클라이언트로 끝내고, 9절 측정 결과로 값을 바꾼다. 시간 제한을 넘으면 대체 번역으로 넘어가므로, 측정할 때 대체 번역 비율도 함께 본다.

### 7.4 원화 가격
- 원화 계산은 **AI가 사진과 대조해 보정한 가격과 통화**를 기준으로 서버가 한다. 환율은 기존 환율 경로(`/lines`의 원화 계산과 같은 방식)를 쓴다(사용자 결정).
- AI가 가격을 확실하다고 하고 통화를 알 때만 `confirmed: true`이고 `krwAmount`를 채운다.
- 불확실하거나 통화를 모르면 `confirmed: false`, `krwAmount: null`이다. 앱은 원문 가격만 보여 주고 "확인되지 않은 가격"으로 표시한다(사용자 결정: 불확실하면 확정하지 않음).
- 대체 번역 문단은 사진 대조가 없으므로 기존 `PriceExtractor`로 가격을 뽑는다. 뽑은 `text`, `amount`, `currency`는 그대로 채우되, `confirmed: false`, `krwAmount: null`로 두고 원화 환산을 하지 않는다. 뽑지 못하면 `prices`는 빈 배열이다(제 판단).
- 대체 번역 문단의 `pronunciation`은 null이다. Google 번역에는 발음이 없다. 앱은 발음 칸을 숨긴다(제 판단, `/lines` 대체 경로와 같은 규칙).

### 7.5 호출 제한
- 기존 번역 호출 제한(`RateLimitBucket`)과 같은 구조로 하되, 사진 API용 한도를 따로 둔다. 숫자는 9절 비용 측정 뒤 정하고, 그 전에는 `/lines`와 같은 개발 초기값을 쓴다. 대체 번역은 한도를 추가로 쓰지 않는다.

## 8. 사용자 확인이 필요한 미정 항목
- 보관·삭제·학습 사용 안내: 서버 구현과 AI 제공업체 정책을 확인한 뒤 문구를 정한다. 그 전에는 앱에 약속 문구를 넣지 않는다(사용자 결정).
- 2048px, JPEG 품질, 모델, 시간 제한, 호출 제한 숫자: 9절 측정 뒤 정한다.

## 8.1 설정값: 개발용 임시값과 측정 후 확정값

| 항목 | 개발용 임시값 | 확정 시점·근거 |
|---|---|---|
| 기준 사진 긴 변 | 2048px | 9절 작은 글씨 인식 품질 측정 |
| JPEG 품질 | 85 | 9절(인식 품질과 크기) |
| 모델 `translation.photo.model` | 테스트는 가짜 클라이언트를 쓴다. 로컬 실연동 기본값은 `claude-sonnet-5-5`(이름만 정해 둠) | 9절 품질·비용·속도 비교 |
| 서버 시간 제한 | 30초 + 글자당 12ms, 최대 90초 | 9절 지연 p90, 대체 번역 비율 |
| `max_tokens` 계수 | `/lines`와 같음 | 9절 usage |
| 앱 HTTP 시간 제한 | 120초 | 서버 최악 시간 + 여유 |
| 문단 한도 | 50개, 문단당 300자, 전체 4000자 | 9절 시료의 실제 분포 |
| 호출 제한 | `/lines` 개발 초기값 | 9절 요청당 비용 |
| multipart 한도 | 파일 5MB, 요청 6MB(기존) | 기준 사진 크기 확정 뒤 |

임시값은 설정이나 상수 한곳에 모으고, 임시값이라는 표시를 남긴다.

## 8.2 실제 연동 순서
1. 가짜 클라이언트로 앱과 서버를 구현하고 테스트한다. 이 단계만으로는 **실제 번역 연동이 완료되었다고 보지 않는다.**
2. 실제 사진을 보내기 전에 AI 제공업체의 데이터 보관·학습 정책과 조직 설정을 확인한다. 그 결과로 동의 안내 문구와 촬영 화면 안내를 검토한다. 바꿀 것이 있으면 안내 버전을 올린다.
3. 개인정보가 없는 시료 사진으로 실제 Claude 호출을 확인한다(9절 측정).
4. 측정 결과로 8.1의 확정값을 정한다.
5. 실기기에서 처음부터 끝까지 확인한다. 그다음 번역 탭을 새 흐름으로 바꾼다(6.0).

## 9. 모델·크기 측정 계획(구현 전 또는 초기 단계)
- **시료**: 메뉴판, 표지판, 안내문, 작은 글씨(영수증·약관), 흐리거나 기울어진 사진을 언어별(ja/zh/en)로 모은다. 개인정보가 없는 사진만 쓴다.
- **비교 대상**: 사진 입력을 지원하는 Claude 모델 후보(예: `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`)와 사진 크기(긴 변 1536/2048/2560 등)
- **측정 항목**:
  - 번역 정확도
  - 지어내지 않는지: 읽을 수 없는 글자를 `[읽을 수 없음]`으로 남기는지
  - 가격 정확도
  - 지연(p50/p90)
  - 요청당 비용(usage 로그의 입력·출력 토큰)
- 결과를 보고 모델, 사진 크기, 시간 제한, `max_tokens`, 호출 제한을 정한다. 크레딧이 있어야 측정할 수 있다.

## 10. 검증 기준(구현 때)
- **앱**
  - 사진 정리: 회전된 EXIF, 가로·세로 사진, 작은 사진(축소 없음)
  - 동의: 처음, 버전 올림, 취소 시 전송 0건, 뒤로가기
  - 늦은 응답: 취소·재촬영·탭 이탈·다시 시도 뒤 도착한 응답 무시
  - 확대·이동 중 상자 위치(사진 좌표와 일치)
  - 상자 누름 → 상세
  - 원문 보기 전환
  - 대체·불확실 표시
  - 응답에 빠진 ID와 모르는 ID
  - 작은 화면, 큰 글자 배율, 긴 번역
- **백엔드**
  - 검증 400 경우들(ID 형식·중복, 크기 불일치, 상자 범위, 한도)
  - AI 성공
  - AI 일부 ID 누락 → 문단별 대체
  - AI 실패 → 전체 대체
  - 대체도 실패 → 503
  - 가격 확정·미확정
  - 429
  - 로그에 사진·글자 없음
  - 외부 호출은 대역으로 처리한다.
